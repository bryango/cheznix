# Manage servers with clan

## Quick commands

- With https://git.clan.lol/clan/clan-core/pulls/6185 in place one can initialize hardware config with a local kexec tarball:
  ```bash
  clan machines init-hardware-config $TARGET --target-host root@$TARGET:$PORT --kexec $TARBALL --debug
  ```
- Build the config with a remote build server and copy the built closure to the target host:
  ```bash
  nixos-rebuild build --build-host $BUILD_SERVER --target-host root@$TARGET:$PORT --flake .#$TARGET --use-substitutes
  ```
  One can also use `nix copy` with related flags.

- In later updates one can simply call `clan machines update $TARGET --upload-inputs`.
  When there is signature issues try `nix copy --to ssh-ng://... --no-check-sigs`.
  Also mix in `--substitute-on-destination`.
  Also probably login as root in the remote target: `ssh-ng://root@...`.

- When run on hostA
    nix copy --from ssh://hostB --to ssh-ng://hostC /nix/store/xxx-path
  the data goes from B to A to C, so A is used as a relay. This may be suboptimal.
  So one should probably ssh into hostB and run the copy there directly.

- Edit secrets: clan vars generate $TARGET --regenerate --generator $SERVICE
## Introduction

Clan integrates all the state of the arts solutions to provision and manage servers
using nix and the NixOS module system.

The documentation is incomplete (as is usual for everything in the nix ecosystem)
but the "Getting Started" guide is mostly adequate for newcomers:
- https://docs.clan.lol/getting-started/

Some notes:
- I first tried to put my clan config (with the autogenerated `flake.nix` and `clan.nix`) in a subdirectory within a monorepo, but the `clan` command fails with a cryptic error. In the end **I put my clan config in a separate git repo at `~/.config/clan`**. Later I found out it seems that one can use [`.clan-flake`](https://docs.clan.lol/guides/inventory/autoincludes/#other-auto-included-files) to tell clan to look at the current directory for configurations (otherwise it seems to always go to the git root).

- The `inventory` config are used for managing config **across a fleet (clan) of machines**. The top-level `machines` config, on the other hand, is used to manage per-machine config.

- After each `clan` command, **the app will automatically commit config changes**. This is a nice touch as it prevents data loss due to my carelessness.

- Clan is **written in python** so it often vomits a bunch of incomprehensible, ugly debug logs when it fails (I don't know why but it seems to be a typical behavior of python apps). On the other hand, it is easy (and fast) to modify and rebuild the app.

For servers one should follow the "Prepare _virtual_ machines" step in the guide:
- https://docs.clan.lol/getting-started/prepare-virtual-machines/

When migrating an existing machine to clan one should regenerate its secrets with `clan vars generate $TARGET`.
